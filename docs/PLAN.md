## Diff 改造报告

### 结论与范围

本节保留改造前的问题与方案，实施状态见紧接的“0.8.3 落地范围”。审查依据为用户提供的真实界面、Droid
`f278b596a93704bcc83625e74a0b4c23d6738821` 的生产调用链，以及 Kilo 源码
`76bcfd40be616a72f4697b3041565f322245b462`。Kilo 的结论只代表该源码版本，
不据此推断其已发布安装包表现。初次报告为只读审查；后续修复及定向回归已获用户授权。

### 0.8.3 落地范围

- D01–D04：无 HEAD 比较、本地 Git 读取、明确 Branch 基线、范围请求身份与失败恢复、默认变更块。
- D06–D10：大正文源会话引用及按需读取、保留活跃快照并按可达性回收、词级高亮、阅读位置与交互提示。
- D13–D18：显式编辑优先返回、全部编辑已查看语义、过滤后导航、完整提交清单、提交版本校验与部分暂存、稳定历史选择与聊天入口。
- D05 保留可靠版本的按需对照，不要求每次工具操作重建全文。D11 单份源码的大规模渲染优化、
  D12 更广撤销、就地展开上下文、换行和批注反馈继续作为后续增强，未纳入本次实现。
- 保留的边界：正文单份 512,000 单元、历史响应 200 条／512,000 单元、源 JSON 解析硬限；
  原始日志缺失无法补造，活跃快照引用也不承诺无限历史。验证与分发事实统一见 STATUS。

建议保留现有 Review、快照和公共 Diff 组件，分批修正数据来源、范围和交互。
当前证据不足以支持推倒重做，也不需要为了每一次 Edit 的全文重写 CLI 执行机制。

本轮方向是：**每次编辑默认看真实改动片段；本轮和 Git 比较按需扩大上下文。**
这取代下方旧计划中“Review 默认完整文件、逐次编辑强求全文”的后续目标。
旧条目的完成标记仅描述当时实现，不表示本文的新改造已经完成。

- 聊天工具卡回答“这次操作改了什么”；本轮汇总回答“这一轮前后工作区有什么变化”。
- Review 默认展示变更块及少量上下文。保留可靠版本的全文能力，但不自动要求每次操作都有全文。
- 完整修改记录仍需保存。取消默认全文不能变成截断补丁、漏文件或取消历史的理由。
- 优先修复无首个提交的 Git 范围、范围切换和证据丢失。文案与失败提示不单独作为交付结果。
- 后续提升阅读、定位和反馈效率；精确逐操作快照、大型渲染器迁移等高成本项目暂缓。

### 一、六种比较范围应有的含义

| 范围 | 回答的问题与比较对象 | 默认入口与显示 | 必须守住的边界 |
| --- | --- | --- | --- |
| Recorded edits | 本轮记录的各次工具操作及结果 | 某条 Edit / ApplyPatch 卡片；定位该次操作的真实片段 | 多次修改分别保留，不把它们相加冒充最终净变化；输入预览不算执行成功 |
| Turn workspace | 本轮开始前 → 本轮结束后；执行中则为开始前 → 当前工作区 | 本轮文件汇总的主入口；默认变更块 | 时间段内可能包含用户或并发任务的改动，不能标作“全部由当前 Agent 修改” |
| Workspace | HEAD → 当前工作区，包括适用的未跟踪文件 | 主动查看仓库当前状态 | 无首个提交时以空树为基线；不要求 AI Runtime 在线 |
| Branch | 指定基分支的 merge-base → HEAD | 主动查看当前分支已提交变化 | 当前 Droid 语义只含已提交变化；不能悄悄加入未提交文件；必须显示比较基线 |
| Unstaged | Index → 当前工作区，包括适用的未跟踪文件 | 查看尚未暂存的变化 | 直接以 Index 为基线，不先解析 HEAD；与 Staged 不能互相混入 |
| Staged | HEAD → Index | 查看准备提交的内容 | 无首个提交时为空树 → Index；文件部分暂存时只显示已暂存部分 |

范围选择器建议按“本轮记录”和“Git”分组，保留上述能力，不新增一个含义重叠的万能范围。
是否增加会话累计净变化暂不纳入首批：现有数据并不天然提供跨轮、跨重连、跨工作区的可靠累计基线。

“完整文件”还要拆开三个概念：完整的 before/after 版本、完整的修改补丁、渲染所有未改动行。
完整补丁支撑单次改动的准确展示；可靠 before/after 支撑扩大上下文和基于版本的比较。
是否渲染全部未改动行属于阅读偏好，操作资格仍由对应证据决定。

### 三、Kilo 值得借鉴什么

| 方面 | Kilo 当前源码的做法 | 对 Droid 的建议 |
| --- | --- | --- |
| 工具过程 | Edit / Write / ApplyPatch 卡片以补丁或提交内容预览为主，放大不意味着拿到了历史全文 | 采用“单次改动片段”的正常产品路径，减少不必要的全文重建 |
| 来源组织 | 来源描述范围、能力、摘要和按文件读取；控制器处理切换、迟到响应、重复读取与可见性 | 在现有 Coordinator 内统一来源能力和请求身份，不先造新框架 |

| Git 详情 | 可按文件读对应版本；渲染器优先消费 patch，控制首屏工作量 | 列表先到、文件详情按需到，版本读取与显示多少上下文分离 |
| Review 反馈 | 批注保存文件、左右侧、行范围和原文，可收集后发回聊天 | 基础读取与定位稳定后，单独补“选中变更 → 写反馈 → 加入聊天”，先形成可审阅的草稿 |

### 四、聊天过程中的 Diff

#### 4.1 工具卡片

建议保持文件名、操作状态、可靠的增删统计和 Review 入口。展开后显示该次真实变更块，
不要自动拉取全文；多文件工具按文件展示。失败、提议、结果不确定与已执行仍沿用真实状态。
不能把“工具结束”直接当作“每个文件都修改成功”，也不能把未知统计渲染为 `+0 −0`。

具体行为：

1. 点击某次 Edit 的 Review，定位同一工具、同一文件、同一编辑记录；展开后的默认内容与聊天片段一致。
2. 保留历史编辑切换；每项用序号、工具名及已有的增删/位置摘要区分，不只重复 `Applied`。
3. 移除该入口默认的 `Request full file context` 及其失败横幅。普通片段阅读不以重建全文为条件。
4. 成功 Create / Write 保存的单份提交内容可以提供“查看保存内容”，但不标作 before/after 比较。
5. “查看本轮工作区变化”作为独立入口，明确切换范围。不能在不告知范围变化的情况下替换某次 Edit。
6. 工具仍在执行时只显示真实预览/进度；结果到达后更新该卡，不反复插入新的文件摘要。
7. 展开片段与打开 Review 是稳定的两个动作。不要再用连接是否正常、是否传入回调来改变同一文件行的点击含义。

这一步要同时停止前端默认全文请求和 Host 相应的自动重建开销；只删报错文本不算完成。
也不立即删除全部重建代码：先查原生 Diff、保存源码和历史入口的直接消费者，再移除确认无用部分。

当前生产入口是 [ComposerChanges](../src/webview-v2/chat/ComposerChanges.tsx)、
[AiOperationSummary](../src/webview-v2/chat/AiOperationSummary.tsx) 和
[OperationDiff](../src/webview-v2/content/OperationDiff.tsx)。未发现生产调用的旧 ReviewDock
不作为扩展目标，避免改了闲置组件却未改变用户看到的界面。
改造需核对主聊天、子聊天、只读 Viewer 和独立 Review 的直接消费者；同一个操作在各入口
应显示相同证据，布局变化不改变操作身份。优先复用现有 scope 与 context 参数，不为改默认值扩协议。

#### 4.2 本轮文件汇总

建议汇总卡默认打开 Turn workspace，并在卡片内保留“编辑记录”入口。同一文件多次修改，
汇总只展示净变化；例如先添加再删除同一行，最终净变化可以为零，但两次操作记录仍在。

运行中汇总随确认结果或工作区版本更新；结束后固定到本轮 after 版本。后续用户手动修改文件，
只能改变主动选择的当前工作区比较，不能回写已结束轮次的 Diff。
工具运行于其他目录、Mission 文档或独立 worktree 时维持原归属，不强塞入主工作区文件表。

### 五、Review 看板与阅读体验

#### 5.1 范围、基线与默认布局

- 保留现有文件树/列表、统一/并排和上下变更导航。首批不重做整体布局、主题或尺寸。
- 所有范围默认变更块；有精确版本的范围支持 3 / 20 / 100 行和全文。之后再考虑在折叠区就地展开上下文。
- 在可见位置显示比较两端，例如 `Index → Working tree`、`本轮开始前 → 本轮结束后`；不能只藏在标题 hover。
- Branch 明确基分支，选择本地已有引用即可；不为了打开 Diff 自动 fetch、创建提交或改变分支。
- 已经选中的操作、范围与菜单选中态保持一致；单份保存源码不使用“全文 Diff”的选中标记。
- 缺少版本、非 Git、没有基分支和没有变化是不同状态。能力不满足的范围有明确原因，不能显示成成功的空列表。

#### 5.2 读得清楚、切换不丢位置

- 先补有限长度修改行的词级强调；复杂重排仍可按行显示，不为漂亮配对做高成本全文匹配。
- 以范围、文件、操作/版本和视图保存阅读位置。内容更新时尽量保留当前 hunk/行锚点，不能只记像素后任其漂移。
- 切统一/并排尽量定位原来阅读的变更；同一文件切回时恢复位置；定位目标未挂载时保留现有虚拟导航能力。
- 搜索和“仅未查看”后，文件导航统一使用当前可见列表；标记后进入下一个仍匹配的文件，不跳到隐藏条目。
- 明确变更导航的首尾行为，优先禁用已到边界的方向；文件列表现有键盘能力继续保留，不另做不一致的快捷键路由。
- 长行保持可横向滚动，复制不包含行号和装饰。自动换行列为独立增强，必须同时解决可变高度和左右对齐。
- 为上下变更、打开文件、更多操作等统一共享 Tooltip；焦点、hover、选中和禁用状态彼此可区分。
- 深色、浅色、VS Code 跟随主题和窄面板都验收。现有 hover 样式先查实际载荷与命中情况，再修改颜色，避免重复叠加样式。

#### 5.3 阅读能力与动作能力分开

显示补丁、扩大上下文、打开保存版本、打开当前文件、标记已查看、撤销、提交是独立能力。
某文件可读并不表示可逆；当前磁盘可打开也不代表历史版本可恢复。
建议让 Host 按真实来源计算能力，UI 消费结果；不要在多个组件根据一条报错字符串猜测按钮是否可用。

“已查看”应绑定实际内容版本，而非文件名或相同增删行数。内容改变后需重新检查；
运行中的文件保持不可最终标记，结束后以已加载且匹配的最终版本为准。已有校验保留，补查范围切换和重载后的身份一致性。

Recorded edits 目前按文件聚合标记，首批建议明确为“标记此文件全部编辑已查看”，并要求
全部记录可访问；不能在只返回截断前缀时暗示已审完全部。暂不新增逐操作已查看协议；
若以后确认有逐条审阅需求，再实现操作级标记与文件聚合，不能继续混用两个粒度。

### 六、数据完整性、版本与保留

#### 6.1 先保证补丁完整，再决定显示多少

当前数据预算分布在不同层：操作补丁总量 24,000 字符单元、完整提交内容 128,000；
Review 单文件响应补丁上限 2 Mi 字符单元；同文件历史传输最多 200 条且片段/提交内容合计 512,000。
这些不是同一种限制，也不等于磁盘存储字节数。见
[Review 协议](../src/shared/protocol/reviewPanelProtocol.ts) 和
[文件读取](../src/extension/review/reviewContent.ts)。

建议把执行结果摘要与大补丁正文分开：

1. 在现有结果采集边界保存实际返回的补丁，摘要只携带文件、状态、版本和正文引用。
2. 聊天先加载摘要；用户展开或打开 Review 时再读所选文件/操作，不批量传整轮历史全文。
3. 正文沿用现有敏感内容过滤和路径边界，另设有界存储额度；预览和 Bridge 传输预算不能继续充当原始补丁保存上限。
4. 区分“完整补丁”“被裁剪的预览”和“源数据未提供”。如 SDK 本身已截断，插件不能凭本地持久化补回缺失内容。
5. 保留受影响文件的已知信息，避免一个大文件让同次工具的全部小文件结果消失。
6. 只提高传输上限不能作为最终方案；必须同时控制保存体积、单次消息体积和可见区域渲染量。

显式选择的工具记录必须优先进入有界返回结果：从第 201 次 Edit 打开时，正文、标题、历史选中项
和 Native 动作都指向第 201 次，不能退选第 200 次。读取其余历史可用有界批次；先修目标身份，
不把它拖到“大文件分页基础设施”完成后。用户未明确选中时，默认项才可以按产品规则选择。

这是 P1 的中等跨层改动，先核实 Runtime 实际收到的内容，再决定持久化位置；不预先发明新的 CLI API。

#### 6.2 轮次版本继续保留，逐操作精确版本暂缓

现有 [turnFlow](../src/extension/chat/turns/turnFlow.ts) 发送本轮前会等待 before 快照采集结束；
[采集失败仍允许发送](../src/extension/chat/changes/snapshotCapture.ts)，只有实际保存成功的快照
才构成可信的执行前基线。相反，[Daemon 通知](../src/runtime/daemon/sessionStream.ts) 先入队，
Host 消费 running 通知时 CLI 可能已经写盘。在监听器里 `await readFile()` 不能变成执行许可钩子。

因此首批继续使用本轮 before/after、Git 对象和真实工具补丁。不要为了某次操作缺全文，
抓取后来磁盘内容来拼成“当时版本”。同一文件由多个子会话并行修改时，没有确定顺序就不跨会话重放。

重连后补拍的 before 只能证明“重新接入时”的状态，不能冒充本轮真正开始前。
若未来需要 Host 退出后仍完整记录版本，应让执行端持久化轮次边界并让 Host 读取，
这是单独的架构工作，不能用又一层 UI 重试代替。

#### 6.3 回收不能一次清空仍有用的历史

先解决正在运行、正在查看和恢复所需版本的引用保留，再调整容量策略：

- 以记录引用决定版本是否可回收；当前任务和打开的 Review 在读取期间持有引用。
- 按明确保留策略逐步淘汰旧轮次；索引记录与对象同时保持一致，不先删对象再留下可点击的历史入口。
- 对共享 Git 对象做可达性回收，而不是简单逐文件相加或整个目录删除。
- 先保证新写入记录可靠；旧版本已经丢失就维持真实边界，不迁移成伪造的完整记录。
- 不承诺无限历史，也不为此增加云同步。保存额度与最近访问策略需结合实际仓库体积决定。

保留策略调整必须与本轮读取、Reload 和清理时机一起验收；只增加“历史已过期”的显示没有解决保留问题。

### 七、实时更新与状态一致性

文件读取已有队列、请求身份、写入结束时的失效处理和离屏释放，应继续使用。
范围切换需要达到同样的完整程度，而不是另做一套独立刷新逻辑。

建议的最小状态模型：

- 区分“当前已显示范围”和“正在请求范围”；请求带唯一标识，成功后一起提交基线、文件清单和选中文件。
- 错误、超时和取消只结束对应请求；清掉它的等待条件，不允许无关操作错误取消新范围请求。
- 迟到响应不得覆盖新会话、新范围或新版本。关闭/失效时释放订阅和挂起任务。
- 原内容在刷新时可以继续阅读，但保留原范围标识；不能把旧正文放在新范围标题下。
- 稳定的历史比较不持续轮询。正在显示的工作区比较合并短时间文件变化；任务结束后必须补一次最终读取。
- 后台不可见时限制重复读取与重算，重新可见时核对版本；不要把所有文件内容随每次状态广播反复发送。
- 区分自动跟随最新结果与用户正在阅读的固定编辑。用户开始查看某次记录后保持该记录；新编辑到达可提示，不在原滚动位置无声替换正文。

最终体验应是：切到 Staged 就展示 Index 对应版本；快速切换也不会看见上个范围的数据；
刷新不无故回到顶部；任务结束后显示最终结果，而不是一直停在 `Updating`。

### 八、原生 Diff、撤销、提交与反馈

#### 8.1 打开原生 Diff / 当前文件

两个动作应明确分开。原生 Diff 使用当前所选比较的两端；“打开当前文件”才读取编辑器中的当前路径。
保存片段不能伪装成完整文件 URI。原生入口只有在版本可读、体积及编码受支持时才应承诺可用；
不能所有预览超限提示都统一指向一个同样有上限的入口。

现状中 Native 仍调用同一套版本读取，再交 VS Code 虚拟文档展示；每侧读取预算为 8 MiB，
仍拒绝二进制和非 UTF-8。它能解决部分 Webview 预览预算问题，无法补回不存在的历史。
先让能力判定与实际读取一致；直接使用 Git 对象 URI 可另行评估，不作为首批必须重写的来源。
见 [Native 读取](../src/extension/review/reviewCoordinator.ts) 与
[虚拟文档展示](../src/extension/changes/vscodeFileDiff.ts)。

行号定位优先支持右侧当前文件；历史左侧和已删除文件应打开对应只读版本。
从历史行跳当前文件时若行号已经漂移，应说明目标是当前文件，不假装精准定位到历史同一行。
复制路径、复制变更文本、打开文件属于低成本便利能力；保留明确作用对象，不新增一排常驻按钮。

#### 8.2 撤销

首批保留现有“确认工具结果的逆向补丁”范围和事务保护。它与“恢复本轮工作区快照”、
“丢弃 Git 改动”、“回到聊天历史并重发”有不同影响，不能合并成一个 Undo。

在准备扩大能力前，必须逐类确认：新增文件能否证明没有后续编辑；删除文件有无完整旧字节；
重命名是否同时知道旧路径、新路径与内容；多会话编辑是否具有可靠顺序。
缺少其中证据就暂缓该类自动撤销，不能为了按钮可点而降低条件。

保留预览后再校验、未保存编辑检查、文件身份检查、冲突阻断和事务恢复。
显示多少上下文不会改变撤销资格；没有全文也不能成为禁止所有精确补丁撤销的笼统理由。

#### 8.3 提交与 Agent Review

Review 当前范围不应被默认为提交范围。Commit 对话框必须明确它面向当前仓库状态，
显示所选文件的暂存/未暂存状态，尤其不能把 Staged 视图里“只看已暂存片段”误解为提交同文件全部当前内容。
保留已有显式文件选择和用户确认边界；不把打开 Diff 变成暂存或提交动作。

当前对话框已有 `Selected files will be staged in full` 提示，后端确实完整 `add` 选中文件。
这是已提示的限制，不应写成偷偷暂存的现有 bug。建议区分“提交当前暂存区”和“暂存所选文件并提交”；
从 Staged 进入时默认保留部分暂存结果。逐 hunk 暂存编辑器不属于这一小步的必要条件。

另外单独修复两个问题：

- 100 个文件的显示/请求限制与完整 Index 校验冲突。先让所有会阻止提交的已暂存项可见，
  再让列表和提交动作支持同一完整集合；可以有界批次读取，不能把所有已暂存文件当作默认同意提交。
- 在确认提交时绑定实际目标的内容或 Index 版本，写入前核对。有变化则重新展示待提交内容，
  不能只验证会话/目录没切换就把新字节当成用户刚审过的版本。这是风险修正，非已发生事故的断言。

当前只支持 VS Code Git API 中唯一且根目录与工作区一致的仓库。多仓库或打开仓库子目录的支持
放到 P2：按明确的 Review root 选择所属仓库，再统一相对路径；不把多个仓库的提交混成一个操作。

Agent Review 是独立模型会话，目前并不等价于“检查眼前这些文件的这个版本”。
首批把范围说清楚；未来如支持指定版本审查，再把基线、文件与版本作为明确输入，
不单靠当前看板名称宣称精准审查。新增自动模型审查不在本次基础改造范围内。

#### 8.4 把反馈送回聊天

在基础读取稳定后加入本地批注：选文件、左右侧、行范围和原文，填写意见，
收集成一份聊天草稿。用户检查后再发送，避免每选一行就启动模型。
批注绑定版本；内容变更后保留原文引用，提示它针对旧版本，不偷偷挪到新行。
第一版不接 GitHub PR 评论、云同步或团队评审，也不另建一套审查任务系统。

### 九、文件类型与边界矩阵

以下是目标能力与验收约束；未逐项运行验证，不能作为现状全部支持的声明。

| 情况 | 建议的阅读行为 | 操作边界与优先级 |
| --- | --- | --- |
| 普通 UTF-8、CRLF/LF、末尾无换行 | 保留原差异与无换行标记；纯换行变化不能消失 | P1 核对；任何写回不得顺带改编码或换行 |
| 新增/未跟踪、删除、空文件 | 正确显示不存在的一侧和变更类型；空文件变化不等于没变化 | P0 随 Git 基线修复一起覆盖 |
| 同一路径的已暂存与未暂存变化 | 两个范围展示各自两端；Workspace 展示总结果 | P0 保证读取，P1 核对提交动作 |
| 重命名、仅大小写改名、路径含中文/空格 | 保留真实路径；目前本地 Git 使用 `--no-renames`，不要声称已经识别所有重命名 | P1 路径正确；重命名识别增强放 P2 |
| 二进制、非 UTF-8、符号链接、子模块、仅权限变化 | 文件清单保留类型信息；不强行解析成普通文本 Diff | P1 核对现有显示；专用二进制/图片比较暂缓 |
| 超大文件、极长单行、生成文件 | 摘要与变更数据保留，详情按需且有预算；非关键语法高亮可省略 | P1 控制数据；换渲染器须先有测量 |
| 工作区外文件、Mission 资料、其他 worktree | 使用已知归属，只读展示可用结果；明确文件根目录 | 不绕过路径与内容限制，不混进主仓库提交/撤销 |
| 非 Git 工作区、无首个提交、缺少基分支 | 前两者分别处理；无基分支只影响 Branch | P0；非 Git 仍可使用有证据的操作记录与轮次快照 |
| 未保存编辑器缓冲区 | 当前工作区与磁盘版本的边界明确 | 不把未保存内容静默写盘，也不在撤销时覆盖 |
| 冲突中的 Index、重连恢复、并行作者 | 明确实际来源与能读取的版本 | 不伪造干净基线；合并冲突编辑器和作者隔离暂缓 |

### 十、实现边界与最小契约调整

| 层 | 继续负责 | 本轮方案中应调整的部分 |
| --- | --- | --- |
| Runtime / Daemon | 接收真实工具输入、结果与执行阶段 | 有需要时持久化原始补丁正文；不让 Host 的通知监听冒充工具执行钩子 |
| Extension Host | 本地 Git、快照、文件读取、路径归属、版本、撤销和提交 | 修 Git 基线；统一范围请求身份、能力计算和按文件读取；完善保留策略 |
| 共享 Bridge | 可验证的请求、状态、文件摘要和详情 | 先稳定范围请求身份与内容能力；大正文引用按实际需要增加，不一次扩展所有未来字段 |
| Droid Webview 适配 | 范围选择、聊天入口、当前会话/轮次和业务动作 | 默认片段、准确入口和加载状态；组合公共 UI 与 Diff 展示 |
| `packages/chat-ui` | 通用 Diff、文件列表、导航、菜单、批注展示 | 词级强调、位置/选区、共享 Tooltip；不引入 Runtime、Droid Bridge 或 VS Code API |

不需要先做通用插件式“Diff 引擎”。沿现有 Coordinator 和读取函数收敛重复判断即可。
确需扩协议时先改共享契约与校验，再按 Runtime / Host / UI 的消费者顺序接通；
旧持久化记录允许继续只含片段，新字段缺失不能被解释为完整历史。

### 十一、分批交付与成本

成本为相对等级：小表示少量同层改动；中表示数个直接消费者或状态协议；大表示执行端、
历史格式或渲染策略变化。没有据此承诺工期，实际估算应在每批实施前按调用链确认。

| 批次 | 交付内容 | 依赖 / 成本 | 完成标准 |
| --- | --- | --- | --- |
| A：先让范围可信 | D01 无 HEAD；D02 本地 Git 解耦；D03 范围请求；默认片段及对应真实入口 | 首批；中 | 新仓库范围能读；断开 AI 仍能看 Git；选择与正文对应；不再默认请求逐操作全文 |
| B：把阅读做顺 | 词级强调、位置恢复、可见基线、Tooltip/hover/focus、历史项区分 | A 的身份稳定后；中 | 同一文件往返不丢位置；长行和选区正常；深浅主题菜单和按钮状态清楚 |
| C：保证记录不轻易丢 | 大补丁摘要/正文分离、按文件加载、快照引用与增量回收、Reload 身份核对 | A；中到大，拆成可独立交付的小项 | 大操作不丢整批小文件；仍被引用的版本不被回收；最终轮次版本重开不漂移 |
| D：打通评审反馈 | 版本绑定的本地批注、行范围引用、收集到聊天草稿 | A+B；中 | 用户可把明确文件/版本/行的反馈送回同一任务，旧版本批注不会误指新内容 |
| E：有证据再扩能力 | 部分暂存语义、更多可逆类型、换行、渲染器评估等 | 各自独立立项；中到大 | 先满足具体真实需求和验证门槛，避免一次把 Review 变成完整 Git 客户端 |

A 可拆成“Git 范围读取”和“聊天/Review 默认片段”两个完整提交，但每个提交都要接通直接消费者。
D13 的显式目标截断错误随 A 修复，D14 的查看粒度随 B 修复。Commit 的 D16 列表阻断和
D17 版本确认列为独立 P1 小批次，不等待 E 的扩展功能；实现提交当前 Index 的新模式再单独评估。
原生入口若存在作用对象不匹配，也应随 A 修复，不能留给视觉增强阶段。

### 十二、验收方案与性能检查

以下是未来执行清单，**本轮未运行这些测试**。新增、修改或运行自动测试仍需用户明确许可；
获准后只覆盖本批行为，不为 CSS 文本、类名或组件包装写测试。

| 场景 | 必须验证的结果 |
| --- | --- |
| 空仓库创建文件，暂存其中一部分 | Workspace / Unstaged / Staged 各自正确；Branch 单独说明基线条件，不向仓库偷偷提交 |
| 同一文件同时有 staged / unstaged 改动 | 各范围字节与 Git 两端一致；Commit 清楚说明提交哪一部分 |
| Runtime 断开而工作区存在 | 本地 Git Review 可读，AI 操作仍按真实连接能力处理 |
| 单次 Edit、同文件重复编辑、改完又还原 | 每条片段有对应操作；整轮净结果可以为零；两者统计不混用 |
| 工具输入未执行、失败、部分文件成功 | 不把输入或失败计入已应用修改，不因一项失败丢其他确认结果 |
| 大补丁、多文件、源端已截断 | 已知文件不消失；完整保存与预览裁剪明确；不虚构源端没有给出的内容 |
| 从预算外的历史编辑卡打开 | 第 201 次或字符预算之外的显式目标不会退选别次编辑；正文与 Native 动作同一身份 |
| 只看 Edit 1/3、正文历史被裁剪 | “已查看”的作用粒度明确；未载入且不可访问的记录不能被默认算作已读 |
| 超过 100 个状态文件、尾部已有 staged 文件 | 所有阻止提交的项可见且可选择；保留未选暂存保护，不让列表限制制造死路 |
| 确认 Commit 前文件或 Index 被其他任务修改 | 识别目标版本变化，重新展示内容；不把新字节静默当成已审阅版本 |
| 切范围后旧请求晚到、切会话、关闭重开 | 原数据不覆盖新目标；错误结束正确请求；不会永久卡在加载 |
| 连续写入后停止、读取期间版本变化 | 最终读取发生；Mark viewed 只绑定实际已读版本；相同行数的改动也能使已查看失效 |
| 结束轮次后再手动修改、Reload | 原轮次比较保持；当前 Workspace 单独变化；丢失旧基线不伪造恢复 |
| 父/子会话并行修改同文件、不同 worktree | 来源和路径不串；没有执行顺序就不拼逐操作全文/撤销 |
| 历史保留边界、存储回收时仍开着 Review | 被引用版本保持可读；被淘汰记录与对象一致；回收不清空当前任务 |
| 原生 Diff 与当前文件入口 | 原生两端与所选范围一致；当前文件不冒充历史；删除侧不会打开错误路径 |
| 撤销预览后用户再编辑、存在未保存修改 | 重新核验；冲突阻断；不覆盖用户新改动；失败可按现有事务记录恢复 |
| 长 Diff、长单行、窄面板、深浅主题 | 无无法到达的改动；导航、横向滚动、复制、菜单键盘和焦点正常 |
| 来回切文件/布局、刷新、离屏释放 | 保持可解释的阅读锚点；选区不被意外清掉；不出现长期空白 |
| 筛选仅 A/C、未查看筛选、标记并跳转 | 进入当前可见列表的下一个文件，不选中侧栏隐藏的 B；焦点仍有效 |
| 本地批注后文件更新、切换任务 | 批注保留原版本/原文；草稿进入目标任务，未经发送不启动模型 |

性能先记录基线，再判断要不要升级 renderer。采集摘要返回、当前文件读取、解析/高亮、
首次可阅读、切文件、重复刷新、内存和可见 DOM 的耗时/规模，区分 Host I/O 与 Webview 渲染。
使用小补丁、大量变更行、极长单行和多文件四类材料；不拿单个空页面证明长 Diff 性能。
保持现有 128 行后分块、64 行一块、选择中不释放和长单行省略语法高亮等措施。
文本选择需覆盖并排左右栏和跨 64 行区块的复制；当前未据静态实现认定跨区块复制完全正确。
若增加文件查找，必须搜索数据并定位未挂载行，不能把浏览器只搜索已挂载 DOM 当作全文查找。
在获得自动化许可前，只做静态检查与允许的构建，由用户在 VS Code 验收真实行为。

实施代码后的交付遵守项目规则：类型检查、预算检查、生产构建、统一 VSIX 校验、
Microsoft VS Code 当前用户全局安装；同步 STATUS / CAPABILITIES 中真正变化的事实，
再按批准范围完成回归。只改本文不会触发重打包、安装或 Reload。

### 十三、明确暂缓的工作

- 每一次工具操作必有精确历史全文：需要执行端版本证据，投入大，当前默认片段方向不依赖它。
- 全量替换为 Kilo 的 Solid UI 或照搬整套 `@pierre/diffs`：现有 React 组件已有分块，需性能/功能证据后再评估。

- 自动猜作者、自动补出缺失快照、自动拿当前磁盘填历史：无法证明真实性，不做。
- 为失败状态继续增加多层替代阅读链路：先修真实数据和请求流程；保留必要错误边界即可。
- 仅为消除禁用按钮扩大撤销/提交权限：不做；必须先具备对应证据和明确作用范围。
