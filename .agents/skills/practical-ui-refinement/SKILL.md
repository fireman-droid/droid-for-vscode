# 实用界面整改

目标是让用户更快看懂当前状态、找到操作并完成选择。沿用已有产品的视觉语言，从具体问题做小而完整的修改；不把局部整改扩展成整页重设计。

## 从问题决定改法

先看用户指出的区域、实际页面和对应生产组件，把“不好看”落到可观察的原因：相关信息被空白隔开、说明重复、控件占满无必要的宽度、独立选项混成一长列，或入口存在但不能完成操作。简短说明准备改善哪一处，然后推进。

检查所改组件的直接消费者与现有设计约定。截图用于理解问题和参考交互，能力、数据和保存行为以当前生产调用链为准。用户只问原因或方案时先解释，不把讨论自动当成全面改版授权。

选择与问题相称的结构：

- 属于同一个值的信息放在一起，例如“模型名 · 等级”。先检查固定宽度、`min-width`、自动外边距和两端对齐，避免把空白当作层级。
- 触发器显示足够识别当前选择的信息；短值随内容收紧，长值截断或换行，操作图标保持可见。表格、表单的必要列对齐仍按页面需求保留。
- 单一选择直接展示选项；两个相关、可独立调整的维度可以拆成菜单行。只有搜索、分组或子菜单确实让选择更容易时才引入，不能每个控件都套两层菜单。
- 减少重复说明和无效入口。保留能帮助用户恢复的错误信息，区分加载中、加载失败、无搜索结果与能力不支持；不能靠隐藏提示掩盖数据未接通。
- 使用产品已有的字号、间距、颜色、圆角和状态反馈。不要为“高级感”追加装饰卡片、徽章、分隔线或解释段落。

## 保留真实行为

先核对接口或 SDK 对该操作暴露了什么，再决定显示什么。某个模型支持一种能力，不代表所有调用场景都开放该参数；参考产品里的开关也不自动成为本产品的能力。

保留已选值、继承项、默认值、禁用原因，以及原来的草稿、保存和撤销语义。筛选不应清空已存选择；重选当前项不应重置其他已调参数。修改选项层级时检查这些行为是否随控件变化而改变。

复用项目现有公共交互组件。缺少能力时，在共享层补齐必要的 primitive 封装，再接业务；公共组件接展示数据与回调，业务层负责目录来源、权限、校验和保存。复用范围覆盖本次请求涉及的消费者，不顺带迁移整个产品。

键盘导航、焦点返回、Portal 和菜单开合交给现有组件体系。需要搜索输入时，确认空格、方向键编辑和 IME 不被菜单快捷键抢走；只补搜索框与选项之间必要的键盘连接。

## 在真实页面收口

遵循项目当前的工具、验证及安装规则，不另设审批流程，也不扩大已有授权。对 Droid 的具体入口与整改证据，按需阅读 [模型选择器案例](references/droid-model-picker.md)。

小样式与简单局部交互只做一次针对性检查，确认用户指出的问题后及时交付。下面的检查项按改动选择，不是每次必须跑完的清单；不默认扩成跨组件回归或另搭独立 Host、隔离环境。用户明确由自己验证或要求停止验收时，停止追加页面和回归检查，按项目规则完成必要的静态检查、一次最终打包与提交，说明未验证项即可。

验证与本次变化直接相关的结果：

- 在真实数据下查看收起和展开状态，确认名称、选中标记、说明和等级来自正确来源。
- 操作被改动的选择流程，核对回显、默认与继承、保存或撤销等受影响行为；不为截图擅自保存用户配置或发送模型请求。
- 只有布局涉及边界时检查长名称、空列表和窄窗口；确认菜单与内容在可用空间内，搜索和键盘操作仍可完成。
- 用户也在操作页面时，重新读取当前状态再行动，不撤销归属不明的草稿。合并一轮相关修改后刷新；不要在每次微调时反复重建整包或重载真实页面。

视觉修改以实际页面对照和项目要求的构建检查为主，不添加匹配 CSS 文本或类名的测试。界面验收收敛后再完成规定的最终构建与打包；出现新修改、失败或未解决问题时才重跑相关检查。缺少真实页面接入时如实说明，不能把静态样稿或模拟数据写成真实验证。

交付时展示最终效果，简短说明改了什么、哪些行为已验证、尚有什么限制。产品能力或设计约定变化写回项目已有文档；提交、打包与安装各自按当前授权执行，不因效果被认可就自动发布或安装。
